# Joyest Enterprise: Backend Plan (Supabase)

Backend architecture, data model, security and operations. See `1-frontend-plan.md` for UI and routing.

## 1. Scope decisions that shape the backend

- **Payments:** no online gateway in v1. The cart becomes an **order request**: saved in Supabase, then opened as a pre-filled WhatsApp message. Admin tracks status and marks payment manually. Paystack (cards and mobile money) is a phase 2 module.
- **Accounts:** visitors check out as guests. Only admin staff have logins in v1. Customer accounts (order history, reorder) can follow later.
- **Content updates:** both the client and developer, so the admin must cover all content types without code changes.

## 2. Architecture

- **Supabase:** Postgres, Auth, Storage, Row Level Security, Edge Functions
- **Next.js server layer:** Route Handlers / Server Actions for order submission, inquiries and revalidation
- **Email:** Resend for transactional email (admin notifications, customer confirmation when an email is given)
- **Hosting:** Vercel (app) and Supabase (data). Domain registered on the client's behalf and transferred to them.
- **Environments:** local (Supabase CLI), staging, production, with migrations in `/supabase/migrations`

### Supabase clients

- Browser client: anon key, public reads only
- Server client (SSR): cookie-based session for admin routes
- Service-role key: server-only, never exposed to the browser

## 3. Data model

| Table | Key fields / purpose |
|---|---|
| `profiles` | `id` (FK to `auth.users`), `full_name`, `role` (`owner`, `editor`) |
| `categories` | `name`, `slug`, `image_path`, `sort_order` |
| `products` | `name`, `slug`, `category_id`, `short_desc`, `description`, `base_price`, `status` (`draft`/`published`), `badges text[]`, `is_featured`, SEO fields |
| `product_variants` | `product_id`, `label` (size/weight), `price`, `in_stock` |
| `product_images` | `product_id`, `storage_path`, `alt`, `sort_order` |
| `product_details` | `product_id`, `ingredients`, `benefits`, `usage`, `nutrition` (`jsonb`) for accordion content |
| `recipes` | `title`, `slug`, `ingredients`, `steps`, `image_path`, `status` |
| `recipe_products` | Join between recipes and products |
| `bundles` / `bundle_items` | Bundle name, price, items and quantities |
| `gallery_items` | `type` (`image`/`video`), `storage_path` or `embed_url`, `caption`, `sort_order` |
| `testimonials` | `quote`, `author`, `photo_path`, optional `product_id` |
| `orders` | `ref`, customer `name`, `phone`, `email`, `address`, `status`, `payment_status`, `notes`, `total`, timestamps |
| `order_items` | `order_id`, product/variant references, `name_snapshot`, `unit_price_snapshot`, `qty` |
| `inquiries` | `name`, `email`, `phone`, `message`, `is_read` |
| `subscribers` | `email` or `phone`, `source`, `consented_at` |
| `site_settings` | Key/value or single-row config: WhatsApp number, hero content, social links, delivery info, announcement bar |

### Notes

- Snapshot product name and price into `order_items` so later price edits don't change past orders.
- Order `ref` is a short, human-friendly code (e.g. `JE-2026-0001`) generated by a Postgres function or sequence.
- Use `updated_at` triggers and soft-delete (`deleted_at`) where history matters.
- Index `slug`, `status`, `category_id`, and `orders.status` / `created_at`.

## 4. Security (Row Level Security)

| Access | Rules |
|---|---|
| Anonymous | `SELECT` on published catalog tables only (`products`, `variants`, `images`, `details`, `categories`, `recipes`, `bundles`, `gallery_items`, `testimonials`, `site_settings`) |
| Anonymous inserts | No direct inserts. Orders, inquiries and subscribers go through a server route or Edge Function that validates input (Zod), rate-limits, and writes using the service role |
| Authenticated admin | Full read/write on all tables via a check on `profiles.role` |
| Owner only | Manage users, change roles, edit sensitive settings |
| Storage | Public-read bucket for catalog media; write access restricted to admins; file type and size limits |

Additional hardening:

- Honeypot field and rate limiting (IP-based) on public forms
- Server-side price recalculation: never trust totals from the browser
- Admin routes protected in Next.js middleware **and** enforced by RLS (defence in depth)
- Regular Supabase backups, with point-in-time recovery if on a paid tier

## 5. Order flow

1. Visitor builds a cart (client-side).
2. Checkout submits to a server route.
3. Server validates, recalculates totals from the database, and inserts `orders` and `order_items`.
4. Server returns the order `ref`.
5. Client shows the confirmation and opens the pre-filled WhatsApp link containing the ref and items.
6. Resend emails the admin (and the customer if an email was provided).
7. Admin updates status: `new` → `confirmed` → `paid` → `delivered` (or `cancelled`) and records payment manually.

## 6. Media and storage

- Buckets: `catalog` (products, recipes, gallery) and `site` (hero, brand assets)
- Resize/compress on upload (client-side before upload, or via an Edge Function)
- Store paths in the database and build public URLs in the app
- Videos: prefer YouTube/TikTok embeds to avoid storage and bandwidth costs

## 7. Cache and revalidation

- Catalog pages use ISR.
- Admin save actions call `revalidatePath` / `revalidateTag` so the public site updates immediately after publishing.

## 8. Monitoring and operations

- Error tracking (Sentry or Vercel logs)
- Uptime check on the home page
- Supabase usage monitoring (storage, bandwidth, database size)
- Seed script with sample categories, products and settings for staging
- Documented runbook: how to rotate keys, restore a backup, add an admin user

## 9. Future (phase 2) options

- Paystack integration (cards and mobile money) with webhook handling
- Customer accounts and order history
- Stock quantity tracking and low-stock alerts
- Discount codes
- WhatsApp Business API notifications
- Newsletter automation
